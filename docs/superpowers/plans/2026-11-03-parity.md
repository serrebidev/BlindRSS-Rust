# Python-to-Rust Parity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close every confirmed source-parity gap in Audit 8 while preserving
the shared Python database/config contract and accessible native interaction.

**Architecture:** Reuse the existing core helpers and provider interface. Repair
application dispatch before adding replacement implementations. Keep network,
subprocess, archive and DB batch work on workers; deliver identity-checked results
through the existing UI message drain.

**Tech Stack:** Rust edition 2024, wxDragon 0.9.24, SQLite/rusqlite, ureq,
libVLC, managed yt-dlp/ffmpeg/ffprobe and the existing Caster port.

**Spec:** [Audit 8](../../AUDIT-8-2026-11-03.md), at Python `2a7eeb3`
v2.5.8 and Rust `1df3af2` v0.1.53. This is a proposed implementation queue;
none of its unchecked tests or tasks is claimed completed by the documentation audit.

## Global constraints

- Python behavior is the spec. Re-read the cited Python implementation before
  each task and check whether either source tree has changed since this audit.
- Open copies of Python-shaped fixtures, never personal data or tracked live
  fixtures. Preserve unknown config fields and non-destructive dual-run behavior.
- Keep core GUI-free. Use existing providers, parsers, controls, command registry,
  worker messages and cache policy before inventing another abstraction.
- Every behavior change needs a failing reproduction/regression first, followed
  by the smallest complete change through application callers. A helper-only
  test cannot close a GUI-wiring finding.
- No secrets or article translation text in logs, fixtures or reports. Automatic
  cookie import remains clearance-only; full sessions require explicit action.
- HTTP/process operations need finite timeouts and cancellation/kill ownership.
  Never touch wx objects from a worker or accessibility RPC thread.
- Preserve fixed Settings/control order by appending controls. Read the shared
  app accessibility build rules before implementation; use native labeled controls.
  Owner screen-reader acceptance remains required; do not add a dedicated audit
  or the removed Accessible Browser as incidental work.
- All live casting tests are restricted to R&B Room (`RB Room`). Other protocols
  use fixtures/mocks unless another target is explicitly authorized.
- Do not edit `.github/workflows/` without the owner's direct OK. Package builders
  and expected integration diffs can be prepared before that final approval.
- Preserve minisign verification before update staging, SHA-256 validation,
  install-local runtime state and retryable staging on failure.
- Close IDs in the current audit and append evidence to `docs/PARITY.md` in each
  implementation batch. Never infer parity from an old resolution paragraph.

## Review focus

- Python-created state: spaced category paths, dotted shortcut keys, populated
  tombstones, playback metadata, older cache/download layouts and view IDs.
- Stale work: changed selection/account/media/model, repeated commands, close
  while busy and delayed results must not mutate the new context.
- Failure mid-write: locked DB/config/DLL, interrupted ZIP/network, invalid
  archive and failed second stage must preserve old working data and retry state.
- Large libraries: old matches beyond current caps, many feeds/tags/comments,
  long/live media and slow origins must remain complete and UI-responsive.
- Disabled/unsupported behavior: no categories, disabled translation/browser,
  missing tool, unsupported receiver/pairing or absent locale must fail honestly
  without launching work, sending private identifiers or destroying fallback text.

Every task below includes tests for its applicable review conditions.

Task numbers are stable references, not an instruction to ignore dependencies.
Use this execution order (independent tasks within a wave may proceed together):

- Wave 1: 1, 2, 3, 4, 5, 6, 7. Task 7 may run immediately in parallel.
- Wave 2: 23, 8, 9, 10, 11, 12. Dependency maintenance precedes media/reader work.
- Wave 3: 13, 14, 15, 17, 18, 19, 20, 21, 22, 16.
- Wave 4: 25, 24, 26, 27, 28, 29, 30, 31. Cookie identity precedes browser wiring.

## Execution and verification pattern

For each task, execute these steps as its own reviewable batch:

1. Read the Python/Rust sites cited by its IDs and all affected callers. Capture
   a failing offline regression at the responsible seam, including app routing.
2. Run that regression and record the expected behavioral failure. Do not mark
   a guessed or unexecuted failure as reproduced.
3. Implement the smallest fix in the named existing modules. Extract a policy
   function only when needed to test actual shared behavior; avoid speculative APIs.
4. Run the focused suite named below plus directly affected existing tests. Do
   the stated manual acceptance where a real platform/control is indispensable.
5. Update audit statuses/PARITY evidence, run `cargo fmt --all` after the final
   code edit, then `cargo clippy --workspace --all-targets -- -D warnings`,
   `cargo test --workspace` and `cargo build -p blindrss`. Add the required
   Windows-target core Clippy check if Windows-specific code changes.

Keep commits reviewable when implementation is requested; this documentation
task does not authorize a release or change the release process. Resolve new
failures before claiming a batch complete. Mark platform acceptance pending if
the necessary real system or owner verification is unavailable.
